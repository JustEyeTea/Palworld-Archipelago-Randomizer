# Style guide

How code in this repository is written, so that a person can read it, understand it and change it by hand. It builds
on [Archipelago's style guide](https://github.com/ArchipelagoMW/Archipelago/blob/main/docs/style.md), which applies
everywhere it has a rule (120-character lines, Python PEP 8 with double quotes, Markdown, HTML, CSS, JS). Where this
guide says more, it wins. How the parts fit together is in [the architecture guide](architecture.md).

Most of this code is written by Claude, an AI model made by Anthropic, at JustEyeTee's direction. These rules exist so
that its maintainer, and anyone else, can follow every file without having written it.

Some files break these rules today. Each is fixed when the code tour reaches it; until then, new code follows the
rules and old code is not made worse.

## Naming

- **Say what it is in words a player would recognize.** Use `tower_level`, not `tl`. Use game terms (Area Pass,
  Paldeck, alpha, fast-travel point) the way the game and this project's docs use them. A *region* is one of the 15
  large locked parts and an *area* one of the game's 75 named places; the full list is under
  [Words](architecture.md#words).
- **Read fields by name, never by position.** Write `tech.level`, not `tech[2]`. Give a row of data a `NamedTuple`
  (Python) or a table with named keys (Lua).
- **Define in-house words once.** Words this project made up, such as *piece* (the smallest part of the map the logic
  knows) or *sphere tier*, are defined in a comment where they are first used.
- **Single letters** are only for a short loop's index or a coordinate (`x`, `y`, `u`, `v`).
- **Constants** are `UPPER_SNAKE_CASE`, with a comment giving the unit and the reason:
  `FREE_LEVEL = 15  # levels anyone reaches in the starting zone`.
- **Game ids get their name beside them.** For example, `"Product_Ingot_Grade_03_Steal"  # Refined Ingot`. Many of
  the game's ids differ from what the game shows.

## Comments

- **Say why, not what, and never when.** The code says what it does. A comment says why it does it that way, or what
  would go wrong otherwise.
- **History belongs in commit messages:** dates, version numbers, quotes from playtests, "was X before". A comment
  describes the code as it is now and must stay true when the code changes.
- **Every file opens with 1-5 lines on its job.** Every function others call has a one-line description of what it
  does.
- **Mark what is untested in game,** as "untested in game". Remove the mark when a playtest confirms the code works.
- **Generated files open with "Generated by <script> from <source>; do not edit by hand."**

## Size and layout

- **A function does one job and fits on one screen:** aim for 40 lines or fewer and no more than 3 levels of nesting.
- **A hand-written file has one topic:** aim for 800 lines or fewer. `main.lua`, `walls.lua` and `menu.lua` are over
  this and get split by topic when the tour reaches them.
- **One statement per line.** Don't stack one-line `if ...: x = y` (Python) or `if ... then x = y end` (Lua).
- **No bare numbers with a meaning.** Give each one a named constant. `0`, `1` and an obvious `2` are fine.
- **Repeat with code, not by typing:** `range(1, 33)`, not the numbers 1 to 32 written out.

## Lua (UE4SS)

UE4SS runs some callbacks on a different thread from the game, over the same Lua state, and Lua code there corrupts
that state. These rules keep the mod's code on the game thread. `mod/test/harness.lua` checks the first three.

- **Never use `ExecuteWithDelay`.** For work later, use the queue in `soon.lua` (`later(n, fn)` runs `fn` after `n`
  core updates).
- **Every key bind only hands off:** `RegisterKeyBind(key, function() ExecuteInGameThread(onKey) end)`, with
  `onKey` built once, when the file loads.
- **`LoopAsync` only hands off, and at 300 ms or slower.** The callback is `ExecuteInGameThread(work)` and nothing
  else.
- **Don't keep game objects across a world change.** Look them up again after loading a world. A handle from the old
  world points at freed memory.
- **Log with the `[PalworldAP]` prefix,** and say what the code found, not just that it ran.
- **Every bug found in game becomes a harness test** that reproduces the game's side of it.

## C++

- **Keep the parts that need no Unreal in their own files** (`ap_bridge.*`, `pal_gift_logic.*`, `image_tools.*`), so
  they are tested on Linux (`cppmod/APConnector/test/`).
- **Functions the Lua mod calls take and return text,** and are listed with their arguments at the top of
  `dllmain.cpp`.

## Tests and commits

- **Run the tests before committing:** `tools/ap_tests.sh` for the APWorld, `tools/lua_harness.sh` for the Lua mod.
  CI builds and tests the C++. Judge a run by its exit code, not by reading its output.
- **Ids never move** (see [Ids never move](architecture.md#ids-never-move)). `test/test_ids.py` enforces it.
- **A change that only makes code clearer** starts its commit message with `readability:` and changes no behaviour.
  The tests prove it; for the APWorld, the same seed must also give the same spoiler log before and after. (Renaming
  an item is the exception: Archipelago sorts the item pool by name before shuffling, so new names place items
  differently. Then compare the location list and the item pool, which must match apart from the names, and check
  the seed is still beatable.)
- **Pocketpair's data stays out of the repository:** no table dumps, textures or maps. Commit the generators, and
  make the data from your own copy of the game.
- **Say plainly when work is AI-written,** in docs and release notes.
